# スロパチ取材 店さがし — 設計仕様

作成日: 2026-09-15

## 1. 目的と利用者

スロパチステーションの取材結果記事を収集し、「この機種を打ちたい」から「どの店に行くか」を決めるための私的な検索サイト。
利用者は作成者本人と身近な数人。URLを知っている人だけが見る想定で、一般公開・宣伝はしない。

## 2. スコープ

| 項目 | 決定 |
|---|---|
| 対象エリア | 東京・南関東・北関東（一覧ページ 3 本） |
| 収集期間 | 訪問日が実行日から 90 日以内の記事 |
| 対象機種 | パチンコとスロットの両方 |
| 店舗の並び順 | 対象機種がピックアップされた記事数の多い順（同数なら直近訪問日が新しい順） |
| 運用 | GitHub Actions で毎日クロール → JSON をコミット → GitHub Pages に公開 |
| 技術 | TypeScript 統一。クローラは Node、画面は Vite + React |

スコープ外: ログイン、ユーザー投稿、記事本文の保存・転載、地図表示、通知。

## 3. データソースの事実（調査結果）

- サイトは WordPress。`https://777.slopachi-station.com/report/{tokyo|minami-kanto|kita-kanto}/` が新着順一覧で、`?paged=N` 相当のページネーションを持つ（実装時にリンク先 URL を確認して追従する）。
- robots.txt は `/wp-admin/` のみ Disallow。記事ページの取得は禁止されていない。
- 記事冒頭の表に「店舗 / 訪問日 (YYYY/MM/DD) / 地域 (都道府県 市区) / 設置台数 / 営業時間」がある。
- 記事内の `<h3>【取材種別】</h3>` 相当の見出し、およびタイトルに取材種別が含まれる。
- パチンコ結果は機種ごとに次の定型:
  `<h4>【機種名】</h4>` → `<pre>全N台中、M台がプラス（P%)</pre>` → `<pre>平均差玉数:+X玉</pre>` → DMM ぱちタウンへのリンク `https://p-town.dmm.com/machines/{id}`。
  「バラエティ」のように DMM リンクが無い見出しもある。
- スロット結果は `台番号 / 機種 / 回転数 / 差枚` の 4 列テーブルが複数、または `プラス台 / 勝率 / 平均回転数 / 平均差枚数 / 出玉率` の縦持ちテーブル + 見出し `【機種名 台番〜台番】` の形式がある。両形式を扱う。
- 記事末尾に「同一店舗の結果記事一覧」があるが、本設計では使わない。

│  │  ├─ parse/
│  │  │  ├─ article.ts      記事 HTML → Article

│  │  └─ main.ts            差分クロールの制御
│  └─ test/fixtures/        実記事 HTML（3〜5 本）
├─ web/                     Vite + React + TypeScript
│  └─ src/
│     ├─ App.tsx
│     ├─ components/        MachineSearch, MachineHero, ShopRow, Filters, ShopDetail

│     └─ styles/tokens.css  デザイントークン
├─ data/

│  ├─ machines.json         機種マスタ（キー・表示名・種別・別名）
│  └─ errors.json           解析失敗した記事の URL と理由

articles.json だけが「正」のデータであり、machines.json は aggregate.ts が毎回 articles.json から作り直す派生物。画面は machines.json のみを読み、「店舗から探す」ビューもこれを店舗側から引き直して表示する。

## 5. データモデル

```ts
type Category = 'pachinko' | 'slot';

interface Article {
  url: string;              // 一意キー
  title: string;
  visitDate: string;        // 'YYYY-MM-DD'
  coverageType: string;     // 例 'るいべえ実践来店', 'スロパチステーション来店取材'
  store: {
    name: string;           // 例 '新！ガーデン八潮'
    prefecture: string;     // 例 '埼玉県'
    city: string;           // 例 '八潮市'
  };
  results: MachineResult[];
  fetchedAt: string;        // ISO 8601
}

interface MachineResult {
  category: Category;
  machineKey: string;       // 'dmm:4714' または 'name:<正規化名>'
  machineName: string;      // 記事上の表記
  units: number;            // 集計対象台数
  plusUnits: number;        // プラス台数
  avgDiff: number;          // 平均差玉(玉) または 平均差枚(枚)。符号付き
  unitNumbers?: string;     // スロットの台番範囲 '604〜609' があれば
}
```

集計（machines.json）:

```ts
interface MachineSummary {
  machineKey: string;
  displayName: string;      // 最頻出の表記
  category: Category;
  aliases: string[];
  shops: ShopHit[];         // ピックアップ回数降順
}
interface ShopHit {
  storeName: string; prefecture: string; city: string;
  hitCount: number;
  lastVisitDate: string;
  avgDiffMean: number;      // 各記事の avgDiff の単純平均
  plusRate: number;         // Σplus / Σunits
  articles: { url: string; visitDate: string; coverageType: string;
              units: number; plusUnits: number; avgDiff: number }[];
}
```

## 6. クローラの動作

1. 3 エリアの一覧を新着順に 1 ページずつ読み、記事 URL と訪問日を集める。
2. 訪問日が 90 日より古い記事が 1 ページ分続いたらそのエリアの走査を止める。
3. articles.json に既にある URL は取得しない。「(予定)」を含むタイトルは結果が無いため取得しない。
4. 新規 URL のみ取得して解析し、articles.json に追記。90 日より古い記事は articles.json から削除する。
5. aggregate.ts で machines.json を再生成する。

礼節と堅牢性:

- User-Agent に用途と連絡先を含めた独自文字列を使う。リクエスト間隔は 1 秒以上。並列取得はしない。
- HTTP 失敗は指数バックオフで 3 回までリトライし、それでも失敗した URL は errors.json に記録して続行する。
- 解析結果が「店舗名・訪問日・都道府県のいずれか欠落」または「results が 0 件」の場合は errors.json に記録し、articles.json には入れない。
- 1 回の実行で新規取得する記事の上限を 300 件とし、初回は複数回に分けて追いつく。

機種キーの決定:

- DMM ぱちタウンの機種リンクがあれば `dmm:{id}`。
- 無ければ機種名を正規化（全角英数→半角、空白除去、「ver.」表記統一、記号の統一）して `name:{正規化名}`。
- 「バラエティ」など機種ではない見出しは除外リストで捨てる。

## 7. 画面

単一ページ。状態は URL クエリ（`?c=pachinko&m=dmm:4714&pref=埼玉県`）に持ち、共有・戻る操作に耐える。

1. **切替**: パチンコ / スロット。
2. **機種検索**: 入力欄。表示名と別名に対する部分一致で候補を出す。何も選んでいない間は、直近 90 日のピックアップ回数上位 20 機種を一覧して選べる。
3. **機種ヒーロー**: 選んだ機種名を大きく表示し、直近 90 日の記事数と店舗数を添える。
4. **絞り込み**: 都道府県、取材種別。複数選択可。
5. **店舗一覧**: ピックアップ回数降順。各行に店舗名・所在地・回数・平均差玉(差枚)・プラス台率・直近訪問日を出す。行内に記事ごとのプラス/マイナスを示す小さなセグメント列を並べる。
6. **店舗詳細**: 行を開くと、その店でその機種が載った記事を日付順に並べ、数値と元記事へのリンクを示す。
7. **店舗から探す**: 店舗名の部分一致で、その店で直近ピックアップされた機種一覧を出す補助ビュー。

空状態は「この機種は直近 90 日で取材に載っていません」など、次に何をすればよいか分かる文にする。

## 8. ビジュアルデザイン（frontend-design スキルに基づく方針）

題材はホールの「台データ」。データカウンターの点灯セグメントと、島の看板・新台 POP の極太文字を手がかりにする。

**カラー（ホールの慣習に従い、プラス＝赤、マイナス＝青）**

| 役割 | 値 |
|---|---|
| 地色 | `#EEF0F3`（涼しい薄灰。データ表の紙面） |
| 面 | `#FFFFFF` |
| 文字 | `#1C2230`（青みの濃紺インク） |
| プラス | `#E03A2F` |
| マイナス | `#2E6FD1` |
| 看板 | `#F5C400`（POP の蛍光黄。ヒーロー専用） |

ダークテーマは地色 `#14171C`、面 `#1E232B`、文字 `#E9ECF1` に差し替え、看板・プラス・マイナスはそのまま使う。

**タイポグラフィ（2 書体）**

- 見出し・機種名: **Dela Gothic One**（Google Fonts）。ホール POP の極太ゴシックを機種名ヒーローにだけ使う。
- 本文・数値・UI: **BIZ UDPGothic**（Google Fonts）。数値は `font-variant-numeric: tabular-nums` で桁を揃える。
- 本文 15px / 行間 1.7、行長 40 字前後。ラベルに英字大文字や余計な見出しを付けない。

**レイアウト（左揃え、1 カラム、最大幅 880px）**

```
┌──────────────────────────────────────────┐
│ スロパチ取材 店さがし      [パチンコ|スロット]│
│ 機種名で探す ▏北斗                        │
├──────────────────────────────────────────┤
│ ██████████████████████████████████████████│ ← 看板黄の帯・全幅
│ █ 真・北斗無双 第5章 夢幻闘双            █│    Dela Gothic One
│ █ 直近90日 取材23件・14店舗              █│
│ ██████████████████████████████████████████│
│ 都道府県 ▾   取材種別 ▾                    │
│──────────────────────────────────────────│
│ 5回  ピーアーク草加          埼玉県 草加市 │
│      ■■■□■  平均+4,620玉  プラス台67%  9/13│
│──────────────────────────────────────────│
│ 4回  新！ガーデン八潮        埼玉県 八潮市 │
│      ■■□□   平均+2,800玉  プラス台50%  9/6 │
└──────────────────────────────────────────┘
```

**原則**

- 大胆さは看板黄の機種ヒーロー 1 箇所に集中させる。その他はカードにせず、罫線 1 本で区切った密な一覧にする。
- 行内のセグメント列（■）は記事 1 件＝1 マスで、平均差玉の符号で赤・青に点灯する。装飾ではなく「何回載って何回プラスだったか」を伝える情報である。
- 角丸・影・グラデーションは使わない。動きは行の開閉のみ。`prefers-reduced-motion` を尊重する。
- フォーカスリングを消さない。コントラストは文字と地色で 7:1 以上を確保する。
- 用語は利用者の言葉で統一する（「取材」「店舗」「機種」「平均差玉」「プラス台」）。

生成物っぽさの点検: 暗地＋蛍光 1 色、クリーム地＋テラコッタ、カードの羅列、Noto Sans 既定、中黒区切りのメタ情報、はいずれも避けている。

## 9. 自動更新とデプロイ

- ワークフローは毎日 JST 6:00 に実行。手動実行も可。
- 手順: checkout → Node セットアップ → crawler 実行 → data/ に差分があればコミット & push → web をビルド → GitHub Pages にデプロイ。
- 差分が無い日はコミットせずデプロイだけ行う（ビルド成果物の再生成は無害）。
- クローラの失敗（例外終了）はワークフロー失敗として通知される。errors.json への記録は失敗扱いにしない。

## 10. エラー処理の方針

| 事象 | 扱い |
|---|---|
| 一覧ページ取得失敗 | リトライ後も失敗ならそのエリアをスキップし、他エリアを続行。1 エリアでも成功すれば正常終了 |
| 記事取得失敗 | errors.json に記録し続行 |
| 記事解析失敗（必須項目欠落） | errors.json に記録し続行。次回実行で再試行する |
| サイト構造の変更で全記事が解析失敗 | 新規記事 0 件かつ errors 10 件以上で異常終了させ、気付けるようにする |
| 画面での JSON 読み込み失敗 | 「データを読み込めませんでした。再読み込みしてください」と表示 |

## 11. テスト

- **パーサ単体テスト（Vitest）**: 実記事 HTML をフィクスチャとして、店舗情報・パチンコセクション・スロット表 2 形式・取材種別・「バラエティ」除外・DMM ID 抽出を検証する。フィクスチャは「るいべえ実践来店」「スロぱちガール来店PS」「スロパチステーション来店取材」の 3 種を最低限含める。
- **正規化・集計テスト**: 表記ゆれの統合、ピックアップ回数順、同数時の日付順、プラス台率、90 日境界の除外。
- **一覧走査テスト**: 一覧 HTML フィクスチャから URL と日付を抽出し、「(予定)」を除外すること。
- **画面テスト（Vitest + Testing Library）**: 機種選択→店舗一覧表示、絞り込み、空状態、URL クエリとの同期。
- ネットワークを使うテストは書かず、fetch 層はモックする。

## 12. 法的・倫理的な留意

- 取材データはスロパチステーションの著作物。保存するのは店舗名・日付・数値・元記事 URL のみとし、本文・画像は保存しない。
- 各行から元記事へリンクし、出典を明示する。
- 私的利用の範囲にとどめ、検索エンジンにインデックスさせない（`<meta name="robots" content="noindex">`）。
